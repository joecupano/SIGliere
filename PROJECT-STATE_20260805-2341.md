## What this is

A local-hardware SIGINT platform, single Ubuntu 24.04 LTS Server box
(`rubberduck`). HF/VHF/UHF signal capture + 802.11 device capture,
exposed to a local LLM through in-process native tools. Zero cloud
dependency.

## Architecture (fixed — do not revisit lightly)

Five-tier stack: **HMI** (Open WebUI :8080, OpenWebRX+ :8073, Caddy) →
**Cognitive** (Ollama, qwen3:14b default) → **Bridge** (producer
scripts, ingest pipeline, DB layer) → **DSP** (radiod, direwolf,
multimon-ng, kismet) → **OS** (Ubuntu 24.04, rootless Podman/Quadlet).
Hardware: RX-888 MkII (HF), HackRF One (VHF/UHF), RTL-SDR (RTL2832U +
R820T, **OpenWebRX+-only, see below**), MT7612U (WiFi), i9 + RTX 5060 Ti.

**Data sinks:** `db/occupancy.db` (RF sightings, radiod-driven) →
`latest.kismet` (WiFi/BT, separate schema, 15-min refresh) → sigid
mirror (weekly) → `/data/audio` (4h ingest + on-demand whisper).

**LLM interface:** four native in-process Open WebUI tools —
occupancy, kismet, sigid_reference, whisper. In-process Python, not
MCP/HTTP. LLM is the correlation engine; no schema merging at DB layer.

**Radiod instances (systemd, `radiod@<instance>.service`):**
- `rx888-hf` — RX-888 MkII, HF, fixed channel list (WWV beacons + ham
  bands), active/running.
- `hackrf-2m` — HackRF One, 2m VHF, fixed channel list, active/running.
  (`mcp-server/config/nodes.json` calls this node `hackrf-vhf-uhf`.)
- `rtlsdr-v4` — **stopped and disabled as of this session.** RTL-SDR is
  now OpenWebRX+-only, permanently, not part of the AI/MCP path — see
  "RTL-SDR: descoped from AI/MCP" below for why. The conf
  (`ingest/ka9q-radio/radiod@rtlsdr-adhoc.conf`) and all the fix work
  are kept in the repo, not deleted, in case this gets revisited.

### `rtlsdr-v4`: full technical arc (closed, for reference)

**Bug 1 (source-level fix applied and confirmed): freq=0 dynamic-channel
bootstrap trap.** A brand-new channel created via `ka9q-python`'s
`ensure_channel()`/`create_channel()` starts at `freq=0` — below this
hardware's tunable floor (`min_hz=24000000`; every startup logged
`[R82XX] PLL not locked!`, fell back to `28.8 MHz`). The channel's own
per-block processing (`radio.c`'s `downconvert()`) checks a freq==0
self-destruct countdown *before* processing any queued follow-up
command, so the command that would move it to a real frequency could
die unprocessed and unacknowledged. Fix: `[AD-HOC]` in
`radiod@rtlsdr-adhoc.conf` boots at a real frequency (`24,920,000 Hz`)
instead of `0`; `radiod_adapter.py`'s `set_frequency()` retasks that
known, already-alive boot SSRC (`24920`, via `RadiodNode.boot_ssrc`)
directly instead of dynamically creating a new channel per request.
Confirmed live: 0.05–0.09s clean success, repeatedly, for a channel's
*first* command after a restart.

**Also found (guarded, not fixed): cross-family mode changes hang.**
Switching demod type on the live boot channel (e.g. `nfm` → `am`)
times out identically to Bug 1's symptom, but is a separate cause.
Guarded in `radiod_adapter.py`: a `boot_ssrc`+`boot_mode` node rejects
a cross-family mode request immediately (~0.02s, never contacts
radiod) instead of hanging 5s.

**Bug 2 (the reason for the descope — open, not fixable from this
repo): the boot channel survives only ONE live command per radiod
restart.** Discovered by testing a *third* request in sequence —
something no earlier test in the investigation had actually done
(every prior "success" was coincidentally the first command after a
restart). A second same-family, frequency-only request — even 5s or
30s later — hangs 5s and fails, and the channel does not self-recover
with time; only a full `radiod` restart clears it.

Root cause traced into `ka9q-radio` source
(`/opt/sovereign-sigint/src/ka9q-radio/src/{radio.c,fm.c}`, commit
`e1224dcd1991637ba8e1caa68cd802e1b22933de`): `demod_thread()`'s outer
loop fully re-enters `demod_fm()` (or the equivalent for other demod
types — `linear.c`, `wfm.c`, `spectrum.c` share the pattern) from
scratch whenever `downconvert()` signals `restart_needed`, which
ordinary frequency retasking triggers, not just demod-type changes
(matches `new filter for chan ...` logging on every successful
command). `demod_fm()`'s first executable lines unconditionally
`FREE(chan->status.command)` on every entry — so a command that
arrives and gets queued while the channel is between demod-thread
invocations (mid-restart) is destroyed before it's ever processed or
replied to. Full writeup with line numbers:
`docs/ka9q-radio-upstream-issue-command-queue.md`.

## Guardrails for future changes

1. **Verify against the repo/box, don't paraphrase or invent** — AST
   introspection, `find`, `systemctl`, config dry-run loads, packet
   capture, source-code grep when docs/comments are suspect. This
   session found two more stale/incomplete conclusions from *within
   its own earlier turns* (the freq=0 fix looked "confirmed working"
   before a third sequential request was ever tested; a mid-session
   hypothesis about noisy multicast traffic didn't hold up against a
   targeted packet capture) — re-verify your own recent conclusions
   the same way you'd verify a stale comment, not just prior sessions'.
2. **Bank fixes fail-loud with a specific fix command**, not silent
   auto-repair. Applied this session in `radiod_adapter.py`'s
   `_ensure_ssrc()`/`set_frequency()` (stage-tracked error messages)
   and the mode-change guard (immediate, specific rejection instead of
   an opaque 5s hang).
3. **Preserve DB schema separation** — Kismet/Bluetooth device-identity
   data stays out of `occupancy.db`.
4. **Never invent frequencies, callsigns, MACs, config parameter names,
   or CLI syntax.** If unconfirmed, say so in the file, don't guess.
   (This session: explicitly declined to guess the native `control`
   TUI's keybindings and read `control.c`'s source instead, twice.)
5. **Public-safe defaults only** in shared examples: callsign `N0CALL`,
   grid `FN30as`, city New York NY, tz `America/New_York`.
6. **Never commit secrets.**
7. **Credentials and interactive auth stay with the operator — but
   this is narrower than previously stated.** Earlier project state
   claimed the agent runs in "a separate sandboxed environment" from
   this box. **That was wrong**, discovered this session: the agent
   has direct shell access on `rubberduck` itself (same user, same
   filesystem, same repo). The actual boundary is narrower: `git push`
   and `sudo` fail for the agent specifically because they need
   **interactive credential entry** that a non-interactive tool call
   has no TTY to satisfy — not because the agent is walled off from
   the box. Confirmed repeatedly: `podman build`/run/rm, `curl`,
   `journalctl`, source greps, `systemctl restart` on the *user*-scoped
   `sigliere-mcp.service` (no sudo needed) all ran directly and worked;
   `sudo systemctl restart radiod@rtlsdr-v4` and `git push origin main`
   both failed with the same auth-prompt error every time, no
   exceptions. **Practical rule:** try the privileged/network command
   directly first; if it fails on a credential prompt, hand the exact
   command to the operator rather than assuming it's unreachable.
   Don't default to relaying every command through the operator "just
   in case."
8. **Filing upstream issues:** no `gh` CLI on this host. Draft as a
   file in `docs/`, hand the operator the exact content and target URL
   to paste into the web form. See
   `docs/ka9q-radio-upstream-issue-command-queue.md` for the pattern
   if this comes up again for a different upstream project.
