## What this is

A local-hardware SIGINT platform, single Ubuntu 24.04 LTS Server box
(`rubberduck`). HF/VHF/UHF signal capture + 802.11 device capture,
exposed to a local LLM through in-process native tools. Zero cloud
dependency.

## Architecture (fixed — do not revisit lightly)

Five-tier stack: **HMI** (Open WebUI :8080, OpenWebRX+ :8073, Caddy) →
**Cognitive** (Ollama, qwen3:14b default) → **Bridge** (producer
scripts, ingest pipeline, DB layer) → **DSP** (radiod, direwolf,
multimon-ng, kismet) → **OS** (Ubuntu 24.04, rootless Podman/Quadlet).
Hardware: RX-888 MkII (HF), HackRF One (VHF/UHF), RTL-SDR (RTL2832U +
R820T, **OpenWebRX+-only**, descoped from AI/MCP — see prior state
file for the full investigation arc, unchanged this session), MT7612U
(WiFi), i9 + RTX 5060 Ti.

**Data sinks:** `db/occupancy.db` (RF sightings, radiod-driven, **not
in git** — see `.gitignore`) → `latest.kismet` (WiFi/BT, separate
schema, 15-min refresh) → sigid mirror (weekly) → `/data/audio` (4h
ingest + on-demand whisper).

**LLM interface:** four native in-process Open WebUI tools —
occupancy, kismet, sigid_reference, whisper. In-process Python, not
MCP/HTTP. LLM is the correlation engine; no schema merging at DB layer.

## This session's work: ka9q-radio / occupancy-DB CLI tooling

Three new scripts added to `scripts/`, all committed in `46982b4`
("Tools for troubleshooting and DB cleanup"):

**`scripts/ka9q-channel-activity-test.py`** — read-only. For every
`radiod@*.conf` found under `ingest/ka9q-radio/`, checks
`systemctl is-active radiod@<instance>`, then (if active) measures a
live per-channel multicast window and reports ACTIVE/quiet/NO-DATA per
channel, using the exact same parsing/measurement code as
`decode/radiod_occupancy_producer.py` (`parse_channels`,
`measure_channel_dbfs`) but **never** calling
`OccupancyDB.record_sighting` — running it does not add rows to the DB.
`--sdr`, `--instance CONFIG_STEM=SYSTEMD_NAME` (for the rtlsdr-v4-style
naming mismatch), `--force`, `--window`, `--threshold-dbfs`. Verified
live: `rx888-hf` showed 14/15 channels ACTIVE, `hackrf-2m` showed
channels present but no data at check time, `hackrf-70cm`/
`rtlsdr-adhoc` correctly reported as skipped (service inactive).

**`scripts/occupancy-db-activity-test.py`** — read-only. Answers "is
the DB updating, and which ka9q-radio (`radiod*`-prefixed source_type)
services are populating it?" Opens the DB via a `file:...?mode=ro` URI
specifically so it can never trigger `OccupancyDB`'s
auto-create-on-open behavior. Reports overall last-write age vs.
`--stale-after-sec`, a per-source table (explicitly distinguishing
`radiod*` sources from the legacy `hackrf`/`rtlsdr` scan producers and
`gnuradio_feature_extraction`), and cross-references configured
ka9q-radio SDRs against `DEVICE_PROFILES` to flag ones with no mapping
(`hackrf-70cm`, `rtlsdr-adhoc` — same gap noted above) and ones whose
producer service is active but not actually writing. `--require-radiod-
activity` for cron/monitoring use (exit 1 if nothing radiod*-sourced
wrote in the window).

**`scripts/occupancy-db-manage.py`** — the write counterpart. `sources`
(list distinct source_type/source_device for picking filter values),
`delete` (by `--after`/`--before`, `--sdr`, `--source-type`,
`--freq`/`--freq-min`/`--freq-max`, AND'd together; refuses to run with
zero filters unless `--all`), `reset` (wipe `sightings`+`signals`, keep
schema). Every subcommand is a **dry run by default**; `--yes` is
required to actually mutate anything, and a checkpointed backup copy is
written to `db/backups/` before any real change unless `--no-backup`.
Deleting sightings recomputes or prunes the affected `signals` rollup
rows rather than leaving them stale. **See the incident below — this is
the tool that caused it, and the specific bug is now fixed and
verified.**

## Incident this session: 8 sightings permanently lost from `db/occupancy.db`

**What happened.** While testing `occupancy-db-manage.py`, `--db`,
`--backup-dir`, and `--yes` were defined on both the top-level
`argparse` parser and its subparsers (via a shared `parents=[common]`
parser) so they'd work whether typed before or after the subcommand.
They don't: argparse's subparsers action re-parses with a **fresh**
namespace and then overwrites the top-level namespace wholesale, so any
of these options given *before* the subcommand (e.g.
`--db test.db delete --yes`) got silently reset to their defaults —
which point at the real `db/occupancy.db`. One such test command,
intended to run against a scratch copy, actually ran `--yes` for real
against the live DB.

**What was lost.** 8 sightings with `source_type='hackrf',
source_device='hackrf-one'` (the legacy single-tuner scan producer,
timestamped 2026-08-04 04:18:36Z — 2m/70cm key frequencies), plus their
8 associated `signals` aggregate rows (correctly pruned to zero by the
tool's own recompute logic, since no sightings remained for those
signal_keys). **Not** the live radiod pipelines — `radiod`/rx888-hf and
`radiod-hackrf`/hackrf-one were untouched and kept writing throughout.

**Why it's unrecoverable.** The tool worked as designed and wrote an
automatic backup before deleting
(`db/backups/occupancy.20260809T005559Z.bak.db`). That backup was then
deleted by the operator-side agent minutes later, mistaken for leftover
test debris from unrelated scratch-copy testing, without first checking
what had actually produced it. `db/occupancy.db` is `.gitignore`d (never
in git history), and no other copy exists on disk — confirmed via
`git ls-files`, `git log -- db/occupancy.db` (empty), and a filesystem
search for other `*.bak.db` copies.

**Impact, plainly stated:** 8 rows out of 128,000+ total (0.006%), from
an inactive legacy source not part of any currently-used capability.
Real, avoidable, permanent data loss nonetheless — not minimized here.

**Fixed and verified.** `--db`/`--yes`/`--no-backup`/`--backup-dir` now
live **only** on the subparsers, not the top-level parser (see the
`NOTE` comment at the top of `main()` in the script). Confirmed live:
`--db X sources` (flag before subcommand) now fails loudly with
`unrecognized arguments`, and `delete ... --yes` (flag after
subcommand) works correctly. A flag being *accepted* is no longer proof
it silently misbehaves — argparse now rejects the misplaced form outright.

## Guardrails for future changes

(Carried forward from `PROJECT-STATE_20260805-2341.md`, items 1–8 —
still apply, not repeated in full here. Adding:)

9. **A CLI flag being accepted without an error is not proof it did
   anything.** `argparse` subparsers silently discard/reset a parent-
   level option's value if it's also defined on the subparser and not
   repeated after the subcommand — this produced a real destructive
   incident this session (see above). When a flag's placement relative
   to a subcommand is ambiguous, test both placements explicitly and
   check the *effect* (e.g. did the right file actually get touched?),
   not just that the command ran without an argparse error.
10. **Never delete a file you didn't create the intent for, without
    first confirming what created it and why.** The backup file deleted
    in the incident above was assumed to be test debris from unrelated
    scratch-copy testing; it was actually the one artifact that made a
    real destructive mistake recoverable. If a file's provenance is
    inferred rather than certain, treat it as significant until proven
    otherwise — especially anything living in a path named `backups/`.
11. **Destructive DB tooling: dry-run by default, `--yes` to execute,
    automatic pre-change backup, and test only against a throwaway copy
    of the real file** — the model `occupancy-db-manage.py` follows and
    the one that failed here at the "test against a copy" step, not the
    tool's own logic.
